# Instrucciones para agentes

## Contexto del proyecto

qaTestGE es una plataforma para gestionar bugs, casos de prueba, ejecuciones y evidencias. La visión y los límites del producto están en [README.md](./README.md); las responsabilidades y los flujos técnicos están en [architecture.md](./docs/architecture.md).

## Reglas de trabajo

- Trata JSON de API, almacenamiento local y proveedores como `unknown`; valida estructura y límites antes de utilizarlo. `as T` no sustituye la validación. Mantén DTO, validadores y OpenAPI alineados.
- Toda operación asíncrona debe conservar su usuario/proyecto de origen. Una respuesta tardía no puede modificar la vista de otro alcance; cubre cambios de proyecto durante lecturas y escrituras con regresiones.
- No reintentes creaciones automáticamente sin idempotencia persistente o reconciliación. Conserva la misma clave y el mismo contenido al repetir una solicitud; abortar fetch no revierte una escritura en el servidor.
- Versiona los documentos locales y migra formatos anteriores sin sobrescrituras silenciosas. Agrupa preferencias relacionadas en una escritura y utiliza exclusión y revisiones para detectar conflictos entre pestañas; un evento `storage` no ofrece exclusión mutua.
- Cambios en migraciones, relaciones, permisos o transacciones requieren integración en PostgreSQL efímero además de unitarias deterministas. Nunca utilices la base personal o productiva para estas pruebas.
- Toda promesa debe tener un responsable de manejar su rechazo. `void` solo se permite cuando la operación captura los fallos o tiene una captura explícita; aplica lint tipado y reglas de hooks sin desactivar errores para ocultar problemas.
- App debe componer capacidades: extrae nueva lógica de dominio, carga y persistencia a módulos/controladores de su área. Reutiliza componentes con contratos claros y evita abstracciones genéricas sin usos concretos.
- Las pruebas unitarias se priorizan exclusivamente en el CORE: reglas de bugs/casos/ejecuciones/evidencias, permisos y autenticación, integridad y concurrencia de datos, importación/exportación y cálculos de negocio. Toda prueba nueva debe identificar una regla y un fallo observable; no crear pruebas unitarias de HTML renderizado, textos estáticos, clases CSS, temas, branding ni cantidades exactas de rutas/catálogos. Revisar presentación con los recorridos de navegador existentes y revisión visual; no duplicar una misma garantía en varias capas ni añadir tests por cambios cosméticos. Conservar las pruebas de seguridad, aislamiento, conflictos y rollback.
- Cada arreglo debe cubrir el fallo observable cuando corresponda: datos inválidos, fallos parciales, cambios de alcance y concurrencia. No añadas pruebas que solo repitan la implementación.
- Los textos con cantidades usan `formatCount`/`pluralize` de `src/utils/pluralization.ts`, incluyendo adjetivos y verbos completos. Verifica 0, 1 y varios; amplía el vocabulario del guardián `product/pluralization` cuando corresponda, sin silenciarlo.
- Usa la escala y las clases BEM de `src/typography.css`: títulos 24–28 px, secciones 20 px, subtítulos 18 px, contenido/acciones 16 px y ayuda 14 px. No introduzcas texto funcional menor de 14 px ni reduzcas botones de creación en móvil; respeta zoom y saltos de línea.

- Captura errores asíncronos con try/catch o captura equivalente; Express 5 los propaga al middleware central. Conserva el código HTTP y devuelve mensajes seguros para 400, 401, 403, 404, 409, 413, 422, 429 y 5xx. Usa el cliente API central y el componente `Alert` para mostrar errores en frontend, sin trazas ni credenciales. Un 401 al comprobar sesión sin autenticar es esperado.

- Mantén las entidades de bugs, casos de prueba, ejecuciones y evidencias relacionadas mediante identificadores y referencias explícitas.
- Trata la IA como una capacidad opcional detrás de una interfaz de proveedor. La aplicación debe seguir siendo útil cuando la IA no esté configurada o no esté disponible.
- La IA propone contenido; una persona debe revisar y confirmar cualquier cambio en datos del proyecto. No envíes evidencias, credenciales ni datos sensibles a un proveedor sin una decisión explícita del usuario y controles de privacidad.
- No presentes funciones documentadas como disponibles si todavía no están implementadas. Actualiza README y arquitectura cuando cambien el alcance o las decisiones técnicas.
- Antes de introducir dependencias, servicios o formatos de datos, revisa el código y reutiliza las convenciones existentes. Evita añadir complejidad que no sea necesaria para la v1.0.
- Valida cambios TypeScript con `pnpm typecheck`, frontend y backend con `pnpm build`, pruebas con `pnpm test`, lint con `pnpm lint` y formato con `pnpm format:check`.
- Para cada paquete de cambios, inspecciona el estado de Git, crea una rama de trabajo dedicada, valida y crea un commit en español con formato Conventional Commits: `<tipo>(ámbito opcional): descripción`. No publiques la rama salvo que el usuario lo solicite.
- Divide los cambios en commits pequeños y coherentes, uno por capacidad o área revisable; evita mezclar funcionalidades independientes.
- Usa tipos claros en commits como `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `build` o `chore`. Ademas agrega mediante una lista desordenada los cambios implementados
- Los botones y enlaces presentados como acciones no llevan subrayado en ningún estado. Deben ofrecer hover, foco visible de teclado y estado deshabilitado diferenciados; conservar contraste en ambos temas y respetar prefers-reduced-motion. Reutiliza src/controls.css y los estilos BEM del componente; Importar utiliza el mismo acento distintivo en todo el producto.
- Toda acción relevante iniciada por una persona debe dar feedback visible y accesible: estado en curso y confirmación concreta o resultado visible al terminar; errores mediante Alert, preservando HTTP y el alcance usuario/proyecto. Crear, editar, eliminar, importar, exportar y cambiar permisos/flujo no deben terminar en silencio. Confirma el éxito solo tras resolver la operación; no dispares alertas de éxito para lecturas automáticas ni para cada respuesta HTTP 200. Verifica también fallos y respuestas tardías.
- Todo panel, tarjeta y cuerpo de diálogo debe reservar espacio interior: 24 px en escritorio y al menos 16 px en móvil. Reutiliza los tokens y clases BEM de src/spacing.css (layout__panel, layout__inset, layout__stack y layout__actions); separa contenido y acciones con gap y evita márgenes globales sobre elementos HTML. Los badges pueden usar la escala compacta; no resuelvas desbordamientos quitando el padding. Los encabezados de diálogo permanecen fuera del cuerpo desplazable.
- Para el frontend, nombra clases CSS nuevas y modificadas siguiendo BEM: `bloque__elemento--modificador`. Mantén los estilos encapsulados en el bloque del componente y evita selectores globales para detalles internos.
- Añade pruebas unitarias en `tests/unit/` con Vitest. Las pruebas deben ser deterministas y no depender de un backend, red ni servicios externos.
- Las skills reutilizables de OpenCode viven en `.opencode/skills/<nombre>/SKILL.md`; respeta el frontmatter requerido por OpenCode y las reglas de IA de `docs/architecture.md`.
- Si estoy en `main` o `qa-env` y solicito una funcionalidad, un arreglo o una refactorización, primero comprueba si hay cambios locales pendientes de subir. Si los hay, no crees una rama nueva; si el árbol está limpio, crea una rama nueva que siga el estándar del repositorio antes de implementar.
- Al terminar cada prompt de trabajo, actualiza `MEMORY.md` con el estado técnico y las decisiones vigentes; mantenlo en menos de 100 líneas y reemplaza información obsoleta en vez de acumular historial.
- Las integraciones con APIs y servicios externos se implementan bajo `servicios/`, con interfaces de proveedor y sin acoplar credenciales o datos sensibles al frontend. Los servicios locales de dominio/API permanecen en `backend/`.

## Estructura y estado conocido

- `src/` contiene el frontend React/Vite en TypeScript.
- `backend/src/` contiene la API Express en TypeScript organizada por modelos, controladores y rutas.
- La API usa PostgreSQL mediante pg y backend/src/repositories/postgres.repository.ts. DATABASE_URL se carga desde backend/.env; no mostrar credenciales ni usar la base local para pruebas destructivas. `pnpm db:setup` instala esquema y migraciones en una base qa_test_ge creada previamente; `pnpm db:migrate` actualiza bases existentes. El seed es manual y opcional; no fusionar ni reescribir migraciones distribuidas.
- `tests/` contiene pruebas unitarias y `backend/tests/` pruebas de endpoints.
- Hay autenticación local con usuarios/sesiones en PostgreSQL y autorización de proyectos por cuenta; cada cuenta representa una persona; Equipos permite aceptar códigos de un solo uso y administrar integrantes, con roles Admin/QA/Dev/Solo lectura por proyecto (propietario: Admin implícito). Las plantillas personales de bugs se guardan en PostgreSQL. La baja desactiva y anonimiza al usuario, revoca sesiones y conserva membresías y recursos QA.
- Bugs y casos de prueba tienen estados limitados por sus modelos y restricciones de PostgreSQL; las actualizaciones se realizan mediante API autenticada y scoped al proyecto.
- Los valores iniciales de cantidades del diseñador se guardan localmente por usuario en el navegador; no requieren migración de base de datos.
- GitHub Actions valida pull requests y pushes a `main` y `qa-env`; los pushes a `main` publican artefactos compilados. No hay despliegue automático a un proveedor.
- No describas IA real, recuperación de contraseña, verificación de correo, MFA o invitaciones por correo como disponibles. Las imágenes adjuntas a casos (007) y archivos generales de evidencia (008, máximo 2 MiB) se guardan en PostgreSQL con autorización por proyecto. La configuración de IA es solo una maqueta. La migración 004 añade usuarios sin asignarles organizaciones existentes; la 005 agrega plantillas por usuario; la 006 permite Suite opcional; la 009 añade tags por proyecto asociados con bugs, casos y ejecuciones; la 010 añade invitaciones de un solo uso, la 011 vincula responsables a membresías del proyecto y la 012 añade claves de creación idempotentes de bugs, casos y ejecuciones. La 013 añade flujos de calidad y planes; la 014 añade comentarios/menciones, avisos internos, permisos por proyecto y auditoría transaccional inmutable. La 016 restaura avisos faltantes de automenciones existentes sin duplicar ni sobrescribir lecturas. La 015 agrega requisitos, tendencias históricas de bugs y lotes idempotentes de tags; Dashboard/Reportes usan agregados del servidor, sin snapshot completo. El contexto actor/requestId siempre es transaccional; no usar variables globales ni estado de sesión reutilizado del pool.
- Las migraciones nuevas deben ser aditivas, quedar registradas en `backend/src/migrations.ts` (usado por `migrate.ts` para instalación y actualización) y documentarse cuando cambien capacidades o límites. La carpeta `servicios/` documenta el límite para integraciones externas; no hay proveedores externos implementados todavía.
- La API valida conectividad y esquema PostgreSQL antes de abrir el puerto; si no inicia, ejecuta `pnpm db:check` (solo lectura) y utiliza `pnpm db:setup` para la instalación inicial o `pnpm db:migrate` para actualizar.
